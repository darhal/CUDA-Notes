# 1.2. Programming Model

## 1.2.1. Heterogeneous Systems
The CUDA programming model assumes a heterogeneous computing system, which means a system that includes both GPUs (device) and CPUs (host).

CUDA applications execute part of their code on the GPU but they always start execution ont he CPU. The host code can use CUDA APIs to copy data between the host memory and device memory, start code executing on the GPU and wait for data copies or GPU cod eto complete. The CPU and GPU can both be xecuting code simultaneously.

The code executed on the GPU is refered to as device code, a function that is invoked for execution on the GPU is called a *kernal* (for historical reasons). The act of starting a kernel ris called launching the kernel. GPU threads operate similarly to threads ont he CPU, despite some differences important to both correctness and performance that will be covered in later sections ([Section 3.2.2.1.1](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html#advanced-kernels-independent-thread-scheduling))

## 1.2.2. GPU Hardware Model
Like any programming model, CUDA relies on a conceptual model of the underlying hardware. Froom CUDA prespective, the GPU can be seen as a collection of *Streaming Multiprocessors* (SMs) organised into groups called *Graphics Processing Clusters* (GPCs). Each SM contains a local register file, a unified data cache and a number of functional units that perform computations. The unified data cache provides the physical resources for shared memory and L1 cache. The allocation of the unified data cache to L1 and shared memory can be configured at runtime. The sizes of different types of memory and number of functional units within an SM vary across GPU architectures.

![](Images\1.2\gpu-cpu-system-diagram.png)

**Figure 2:** A GPU has many streaming multiprocessors (SMs), each of which contains many functional units. Graphics processing clusters (GPCs) are collections of SMs. A GPU is a set of GPCs connected to the GPU memory. A CPU typically has several cores and a memory controller which connects to the system memory. A CPU and a GPU are connected by an interconnect such as PCIe or NVLINK.

### 1.2.2.1. Thread Blocks and Grids
A kernel is launched with often millions of threads which are organised into thread blocks. Threads blocks are organized into a grid sharing the same size and dimensions.
![](Images\1.2\grid-of-thread-blocks.png)
**Figure 3:** Grid of Thread Blocks. Each arrow represents a thread

Thread blocks and grids mabe 1, 2 or 3 dimensional to simplify the mapping of individual threads to units of work or data items.

Kernels are launched with execution configuration which specifies the grid and thread block dimensions, it can also include optional paramters such as cluster size, stream and SM configuration settings.

Using built-in variables, each thread executing the kernel can determine the dimensions of the thread blocks and the grid on which the kernel was launched, giving each thread a unique identifier that can be used to determine what data or operation the thread is responsible for.

All threads of a thread block are executed on a single SM, allowing them to comunicate and synchronize with each other effeciently. Threads in a thread block all have access to the on-chip shared memory, which can be used for exchanging information between threads of a thread block. 

A grid may consist of millions of thread blocks, the GPU executing the grid may have only tens or hunderds of SMs. All threads of thread block are executed by a single SM and mostly run to completion on that SM ([CUDA Dynamic Parallelism](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/dynamic-parallelism.html#cuda-dynamic-parallelism) allow a thread block to be suspsended to memory to free up the SUM to execute other thread blocks, similar to context swapping on CPUs. This is not common.). A thread block cannot rely on results from other thread blocks as there is no guarantee of scheduling between thread blocks.
![](Images\1.2\thread-block-scheduling.png)
**Figure 4:** Each SM has one or more active thread blocks. In this example, each SM has three thread blocks scheduled simultaneously. There are no guarantees about the order in which thread blocks from a grid are assigned to SMs.

CUDA enables arbitrarily large grids to run on GPUs of any size, to achieve this, the CUDA model, with some exceptions, requires that there be no data dependencies between threads in different thread blocks (a thread should not depend on results from or synchronize with a thread in different thread block of the same grid). Different thread blocks within the grid are scheduled among the available SMs and may be executed in any order.

#### 1.2.2.1.1. Thread Block Clusters
GPUs with compute capability (CC) 9.0 or higher have an optional level of grouping called *clusters*. Clusters are a group of thread blocks which, like thread blocks and grids can be laid out in 1 to 3 dimensions. Specifying clusters does not change the grid dimensions ot he indicies of a thread block within a grid.

![](Images\1.2\grid-of-clusters.png)
**Figure 5**: When clusters are specified, thread blocks are in the same location in the grid but also have a position within the containing cluster

Clusters groups adjacent thread blocks which provides additional opportunities for synchronization and communication at the cluster level. All thread blocks in a cluster are executed in a single GPC. Because the thread blocks are scheduled simultaneously and within a single GPC, threads in different blocks but within the same cluster can communicate and synchronize with each other using [Cooperative Groups](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html#writing-cuda-kernels-cooperative-groups). Threads in clusters can access the shared memory of all blocks in the cluster, which is refered to as [distributed shared memory](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html#writing-cuda-kernels-distributed-shared-memory). The maximum size of a cluster is hardware dependent and varies between devices.
![](Images\1.2\thread-block-scheduling-with-clusters.png)
**Figure 6**: When clusters are specified, the thread blocks in a cluster are arranged in their cluster shape within the grid. The thread blocks of a cluster are scheduled simultaneously on the SMs of a single GPC.

#### 1.2.2.2. Wraps and SIMT
Within a thread block, threads are organized into groups of 32 threads called *warps*. A warp executes the kernel code in Single Instruction Multiple Threads (SIMT) paradigm. In SIMT, all threads in the warp execute the same kernel code, but each thread may follow different branches.

When threads are executed by a warp, they are assigned a warp lane. Warp lanes are numbered 0 to 31 and threads from a thread block are assigned to warps in a predictable fashion detailed in [Hardware Multithreading](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html#advanced-kernels-hardware-implementation-hardware-multithreading).

If some threads within a warp follow a control flow branch while others do not, the threads which do not follow the branch will be masked off, while the threads which follow the branch are executed. This is called warp divergence, GPU utilization is maximized when threads within a warp follow the same control flow path.
![](Images\1.2\active-warp-lanes.png)
**Figure 7**:  Only threads with even thread index execute the body of the if statement, the others are masked off while the body is executed.

In SIMT, all threads in a warp progress through the kernel in lock step. Hardware execution may differ so exploiting knowledge of how wrap execution is actually mapped to real hardware is discouraged (see [Independent Thread execution](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html#advanced-kernels-independent-thread-scheduling). Hardware may optimize masked lanes in ways that are transparent to the program as long as the programming model is followed, if the program violates this model, this can result in UB (undefined behaviour) that can be different on different GPU hardware.

Understanding the warp execution model is helpful in understanding concepts such as [global memory coalescing](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html#writing-cuda-kernels-coalesced-global-memory-access) and [shared memory bank access patterns](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html#writing-cuda-kernels-shared-memory-access-patterns). Some advanced programming techniques use specialization of wraps within a thread block to limit thread divergence and maximize utilization, making use of knowledge that threads are grouped into warps when executing. 

Thread blocksq are best specified to have a total number of threads which is multiple of 32, while its legal to use any number of threads but when its not multiple of 32 the last warp of the thread block will have unused lanes leading to suboptimal functional units utilization and memory access for that warp.

**Note:** SIMT is often compared to SIMD (Single Instruction Multiple Data) but SIMD follows a single control flow while SIMT each thread is allowed to follow its own control flow path. Because of this, SIMT does not have a fixed data width like SIMD. (See [SIMT Execution Model](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/advanced-kernel-programming.html#advanced-kernels-hardware-implementation-simt-architecture))

#### 1.2.2.3. Tile Programming in CUDA
In addition to SIMT, CUDA supports a tile programming model. In tile programming, the code is written at the level of an entire thread block, describing operations on multidimensional collections of data called **tiles**. The compiler maps these operations to the individual threads of the block.

Tile kernels are launched on a grid of blocks, each block executes the tile kernel and can query its position within the grid to determine which portion of the data its responsible for. The programmer specifies only the grid dimensions; the number of threads per block is determined by the compiler based on the tile operations in the kernel.
![](Images\1.2\tile-simt.png)
**Figure 8:** In SIMT, the programmer writes per-thread code and controls how each thread accesses data. In tile programming, the programmer writes per-block code that operates on tiles; the compiler maps operations to the threads of the block.

Within a tile kernel, the block executes a single control flow. The programmer specifies operations on tiles and the compiler distrbutes the work across the threads of the block. Control flow constructs such as conditionals and loops are supported but because the block follows a single control flow, there is no concept of warp divergence. Scalar operations like computing an index or loop bound are executed by a single thread of the block. Tile operations, such as adding two tiles element by element are collectively executed in parallel by all threads of the block.

Its important to not confuse blocks (unit of execution) with tiles (units of data). A single block may create and operate on many tiles of different shapes and data types.


##### 1.2.2.3.1. Arrays and tiles
Tile kernels work with two types of data: **arrays** and **tiles**. An array (or global array) is a multidimensional container of elements stored in device memory. Arrays are mutable by store operations within a kernel and the have a shape and a data type.

A tile is multidimensional collection of calues that exists only within tile code and is local to single block. Tiles are immutable: every operation on a tile produces a new tile rather than modifying an existing one. Unlike an array a tile doesn't necessarily have a representation in memory (compiler decides how tile data is stored, and may use registers, shared memory or other resources of the SM). Each dimension of the tile must be a power of two and must be known at compile time. Tiles can't be passed as kernel paramters; they are created and consumed entirely withint ile code.

##### 1.2.2.3.2. Tile space and data movement
Data moves between arrays and tiles through load and store operations using a concept called the **tile space**, which is the result of partitioning an array into equally sized, non-overlapping tiles. 

Example: a two dimensional array of shape (M, N), if a load operation specifies a tile shape of $(t_m, t_n)$ the array is conceptually divided into $\lceil{M/t_m \rceil}$ rows and $\lceil{N/t_n \rceil}$ columns of tiles. An index into this tile space (i,j) identifies which tile to load. The load returns a tile of shape $(t_m, t_n)$ containing the corresponding elements from the array. When a tile extends beyond the boundaries of the array (e.g. at the edges when the array dimensions are not exact multiples of the dimensions) the load specifies how out-of-bound elements are handled (e.g. filling them with zeros).
![](Images\1.2\tile-data-movement.png)
**Figure 9:** A two-dimensional array of shape (M, N) is conceptually partitioned into a grid of tiles with shape (tm, tn). A load at tile-space index (i, j) returns the corresponding tile. At the array boundary, elements that fall outside the array can be filled with zeros. A store writes a tile back to the array at a given tile-space index.

A store operation performs the inverse: given a tile and an index into the tile space, it write sthe tile elements to the corresponding region of the array, any writes of out of boundaries are silently discarded. Tile programs support gather and scatter operations, which load from or store to arbitrary positions in an array.

##### 1.2.2.3.3. Operations on tiles
Tile programs provide a set of built-in ops that act on tiles, including elementwise arthmetic, matrix multiplication, reductions (sum, max, min, etc) along one or more axes, shape manipulation (such as reshape and transpose) and type conversion. When two tiles of different shapes are combined in an operation, the smaller tile is auto expanded to match the larger one before the operation is applied.

##### 1.2.2.3.4. Relationship to SIMT programming
Tile and SIMT programming coexist within CUDA, an application may contain both and both types of kernels can operate on the same data in device memory. The choice of the programming model is a per kernel decision. SIMT provides fine grained control over individual threads which remains necessary for some algorithms and optimization techniques. Tile programming provides a higher-level abstraction that can simplify kernel development. Because thread-level decisions are left to the compiler, the same tile kernel can run on different GPU architectures without requiring changes to the source code. Both models are built on the same underlying hardware (SMs, thread blocks and grids) and use the same device memory spaces.

## 1.2.3. GPU Memory
Efficiently utilizing memory is just as important as maximizing the use of functional units performing computations. GPUs contain various types of programmable on-chip memory in addition to caches. The following sections introduce these memory spaces in more details.

### 1.2.3.1. DRAM Memory in Heterogeneous Systems
CPU and GPU both have directly attached DRAM chips. In systems with more than one GPU, each has its own memory. DRAM attached to the GPU is called global memory as its accessible to all SMs in the GPU which does not mean its necessarily accessible everwhere within the system;. DRAM attached to the CPU is called system or host memory.

GPUs use virtual memory addressing. The CPU and GPU use a single unified virtual memory space meaning that the virual memory address range for each GPU in the system is unique and distinct from the CPU and every other GPU in the system. For a given virtual memory address, it is possible to determine wether its in GPU or system memory and which GPU memory contains that address (on multiple GPUs systems).

CUDA APis allow us to allocate GPU or CPU memory and to copy between allocations on the CPU and GPU, within a GPU or between GPUs in multi-GPU system. The locality of data can be explicitily controlled when desired. 

#### 1.2.3.2. Locality Domains:
A *locality domain* is a subset of a GPU's memory and SMs. All GPUs have at least one, larger GPUs may have more than one locality domain. On these with more than one, performance of some kernels can be improved by using localized memory and compute. *Localized memory* is a memory allocation contained entirely within a single locality domain. Kernels using this memory can be scheduled on SMs with the same locality domain. Applications benefit from localization when memory and compute are divided between locality domains and work can be issued to each locality domain in parallel.

GPu memory which is allocated without specifying a locality domain is said to be *unlocalized*. Unlocalized memory allocations span across locality domains, except in the case of very small alocations.

On GPUs with only one locality domain, all SMs and memory are part of that one locality domain.

[Section 4.8](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/locality-domains.html#locality-domains) shows the mechanism for localizing GPU memory and compute within a specific locality domain. Locality domains are a performance feature, CUDA code which does not localize memory or compute will still execute correctly.

Locality domains are mainly used to limit execution/memory allocation within a single GPU die in multi-die GPUs (datacenter B100/B200 class GPUs). On consumer GPUs since they have single GPU die in single GPU package, locality domains are of no use.

#### 1.2.3.3. On-Chip Memory in GPUs
In addition to the global memory, each GPU has some on-chip memory. Each SM has its own register file and shared memory. These are part of the SM and can be accessed extremely quickly from the threads executing within the SM.

Register file sotres thread local variables (usually allocated by the compiler). The shared memory is accessible by all threads within a thread block or cluster and can be used to exchange data between threads of a thread block or cluster.

The register file and unified data cache in an SM have finite sizes. The size of an SM's register file, unified data cache and how the unified data cache can be configured for L1 and shared memory balance can be found in [Memory Information per Compute Capability](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html#compute-capabilities-table-memory-information-per-compute-capability). The register file, shared memory space and L1 cache are shared among all threads in a thread block.

To schedule a thread block to an SM, the total number of registers needed for each thread multiplied by the number of threads in the thread block must be <= to the availble registers in the SM. If thats not the case, the kernal is not launchable, the number of threads in the thread block must be decreased to make the thread block launchable.

Shared memory allocations are done at the thread block level. Unlike register allocations which are per thread, allocation of shared memory are common to the entire thread block.

#### 1.2.3.3.1. Caches
In addition to programmable memories, GPUs have both L1 and L2 caches. Each SM has an L1 cache which is part of the unified data cache. A larger L2 cache is shared by all SMs within a GPU. Each SM has also a seperate [constant cache](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/writing-cuda-kernels.html#writing-cuda-kernels-constant-memory) which is used to cache values in global memory that have been declared to be constant over the life of the kernal (the compiler mau place kernel params into constant memory as well, this can improve kernel performance by allowing kernel params to be cached in the SM separtely from L1 data cache).

#### 1.2.3.4. Unified Memory
Memory is allocated explictly on the GPU or CPU, that memory is only accessible to code running on that device (GPU memory can be used by the GPU only and CPU memory can be used by CPu only) [with exeption to [mapped memory](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html#memory-mapped-memory) which is CPU memory allocated with properties that enable it to be directly accessed from the GPU. However mapped access occurs over the PICe or NVLINK connection]. CUDA API for copying memory between the CPU and GPU are used to explictily copy data to correct memory.

A CUDA feature called *unified memory* allows applications to make memory allocation which can be accessed from CPU or GPU. The CUDA runtime or underlying hardware enables access or relocates the data to the correct place when needed. Optimal performance is attained by keeping the migration of memory to a minimum and acessing data from the processor directly attached to the memory where it resides as much as possible.

The hardware features of the system determine how access and exchange of data between memory spaces is achieved. Section [Unified Memory](https://docs.nvidia.com/cuda/cuda-programming-guide/02-basics/understanding-memory.html#memory-unified-memory) introduces the different categories of unified memory systems. Section [Unified Memory](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/unified-memory.html#um-details-intro) contains many more details about use and behavior of unified memory in all situations.
