# 1.3. The CUDA Platform
Introduction to some of the fundamental concepts/components of the CUDA platform 

### 1.3.1. Compute Capability and Streaming Multiprocessor Versions
Every NVIDIA GPU has a COmpute Capability (CC) number, which indicates what features are supported. The specifications are documented in [Section 5.1](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/compute-capabilities.html#compute-capabilities). A list of all NVIDIA GPUs and their CC is maintained on [CUDA GPU Compute Capability page](https://developer.nvidia.com/cuda-gpus).

CC is denoted as a major and minor version number in the format of X.Y where X is the major and Y is the minor version number.. The CC directly corresponds to the version number of the SM. For example, the SM within a GPU of CC 12.0 have SM version `sm_120`, which is used to label the binaries.

### 1.3.2. CUDA Toolkit and NVIDIA Driver
*NVIDIA Driver* can be thought of the operating sysem of the GPU. Its must be installed on the host system's operating system and is necessary for all GPU users and is foundational to the CUDA platform. In addition to CUDA, the NVIDIA provides all other methods of using GPU for example Vulkan and DIrect3D. THe NVIDIA Driver has version numbers such as r580.

The *CUDA Toolkit* is a set of libraries, headers, and tools for writing, building and analyzing software which utilizes GPU computing and its a separate product from the NVIDIA driver.

The *CUDA runtime* is a special case of one of the libraries provided by the CUDA Toolkit. The CUDA runtime provides both an API and language extensions to handle common tasks such as allocating memory, copying data between GPUs and other GPUs or CPUs and launching kernels. The API components of the CUDA runtime are referred to as the CUDA runtime API.

#### 1.3.2.1. CUDA Runtime API and CUDA Driver API
*CUDA runtime API* is implemented on top of a lower-level API called the *CUDA driver API*, which is an API exposed by the NVIDIA Driver. This guide focuses on the APIs exposed by the CUDA runtime API.  All the same functionality can be achieved using only the driver API if desired. Some features are only available using the driver API. Applications may use either API or both interoperably. Section [The CUDA Driver API](https://docs.nvidia.com/cuda/cuda-programming-guide/03-advanced/driver-api.html#driver-api) covers interoperation between the runtime and driver APIs.

### 1.3.3. Parallel Thread Execution (PTX)
A fundamental yet invisible layer of the CUDA platform is the *Parallel Thread Execution (PTX)* virtual instruction set architecture (ISA). PTX is a high-level assembly language for NVIDIA GPUs, providing an abstraction layer over the physical ISA for real GPU hardware.

Domain-specific languages (DSLs) and compilers for high-level languages can generate PTX code as an intermediate representation (IR) and then use NVIDIA's offline or JIT compilation tools to produce executable binary GPU code.

Since GPU capabilities change and grow over time, PTX virtual ISA is versioned. PTX versions, like SM versions correspond to CC. PTX which supports all the features of CC 8.0 is called *compute_80*.

Full documentation on PTX can be found in the [PTX ISA](https://docs.nvidia.com/cuda/parallel-thread-execution/index.html).

### 1.3.4. Cubins and Fatbins
CUDA is written in C++, that is then compile dto PTX, then PTX is compiled into real binary for physical GPU called CUDA binary, or *cubin* for short. A cubin has a specific binary format for specific SM verison (such as *sm_120*).

Executeables and library binaries that use GPU computing contain both CPU and GPU code. The GPU code is stored within a container called a *fatbin*. Fatbins can contain cubins and PTX for multiple different targets so that the best binary for the running GPU can be selected and loaded.

### 1.3.4.1. Binary Compatibility
NVIDIA GPUs guarantee binary compatibility within a major version of compute capability, GPUs with minor compute capability greater than or equal to the targeted version of cubin can load and execute that cubin. A cubin with code compiled for CC 8.6 can be executed on a GPU with CC 8.6 or 8.9, it can't however be loaded on GPUs with CC 8.0, because the GPU's CC minor version 0 is lower than the code's minor version, 6.

Binaries are not compatible between major CC versions that is cubin compiled for CC 8.6 will not load on GPU of CC 9.0.

### 1.3.4.2. PTX Compatibility
PTX code loaded by an application at runtime is compiled to bianry code by the device driver (called JIT). JIT increases application load time, but allows the application to benefit from any new compiler improvments coming with each new device driver. It also enables applications to run on devices that did not exist at the time of the application was compiled.

JIT compiled PTX code by the device driver is automatically cached to avoid reapeating the compilation in subsequent invocations. The cache is called *the compute cache* is automatically invalidated when the device driver is upgraded, so that application can benefit from improvments in the new JIT compiler built into the device driver.

How and when PTX is JIT compiled at runtime is somewhat relaxed, allowing flexibility for when and if JIT compile some or all kernels. The section [Lazy Loading](https://docs.nvidia.com/cuda/cuda-programming-guide/04-special-topics/lazy-loading.html#lazy-loading) describes the available options and how to control JIT behavior. [CUDA Environement Variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-environment-variables) can also control JIT behavior.

As an alternative to `nvcc` to compile CUDA C++ device code, NVRTC can be used to compile CUDA C++ device code to PTX at runtime. NVRTC is a runtime compilation library for CUDA C++.

### 1.3.4.4. Binary Finalization
Starting with CC 10.0, intra-family binary compatibility is software managd by the NVIDIA driver which extends the binary representation to provide intra-family compatibility.  A binary generated (finalized) for a specific target architecture may execute directly on the target architecture or may be re-finalized at runtime to any GPU which is guaranteed to have binary compatibility. Cubins for compute capability 9.x and earlier are not eligible for runtime re-finalization.

Off-target finalization is the process of binding the cubin, through JIT finalization, to the architecture of the target GPU (in case of different but compatible architecture int he same GPU family). Off-target finalization of a cubin re-finalizes an existing cubin for another compatible architecture. Off-target finalization is significantly less expensive than PTX JIT compilation, but it can still increase module load time relative to on-target execution.

Off-target finalization enables off-target execution, where a cubin finalized for one architecture runs on another compatible architecture in the same GPU family. Execution is considered on-target when the cubin is loaded on the architecture for which it was generated. No further finalization is required for on-target execution.

As with PTX JIT compilation, the NVIDIA driver may cache the results of off-target finalization of cubins to avoid repeating finalization work in subsequent invocations of the application. The cache is controlled by the same CUDA cache environment variables described in [Section 5.2.2](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-environment-variables-compilation).

#### 1.3.4.4.1. Lazy Function Finalization
Lazy Function Finalization (LFF) is enabled by default for off-target finalization. Instead of finalizing an entire cubin when it is loaded, under LFF the driver waits until a kernel is launched and finalizes that kernel and any device functions that it may call.

LFF can reduce load time when an application loads a large module but uses only a small subset of its kernels. For example, an application may link against a large library while launching only a few of its kernels.

LFF may not be beneficial when an application uses most of the functions in a module. Eager finalization can use multiple CPU threads, and its results can be stored in the compute cache. When LFF is active, parallel finalization and caching are both disabled. To compare LFF against parallel eager finalization, use:
```
CUDA_DISABLE_FUNCTION_LAZY_FINALIZATION=1
CUDA_BINARY_LOADER_THREAD_COUNT=<N>
```

The equivalent driver API option for setting the thread count is `CU_JIT_BINARY_LOADER_THREAD_COUNT`. See [CUDA Environment Variables](https://docs.nvidia.com/cuda/cuda-programming-guide/05-appendices/environment-variables.html#cuda-environment-variables) for additional controls.
